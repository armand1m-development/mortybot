🤖 MortyBot — how the LLM assistant works

MortyBot is a grammY Telegram bot composed of skill modules. One of them, assistant, turns @mentions into turns of an agentic loop against an OpenAI-compatible endpoint, with three families of tools: built-ins, MCP tools (web search), and every bot command exposed as a bot_* tool. Static file references are in each section.

1Update routing — what even reaches the assistant

Every Telegram update flows through the grammY middleware chain (session, configuration, i18n, and the assistantApi middleware that prepares the tool set). Skill listeners are registered as forks, so the command chain, the filters skill and the assistant listener all see the same message concurrently. The assistant then runs four gates of its own and quietly steps aside — returning { handled: false } — whenever one fails.

2Turn pipeline — from accepted message to model request

Once the gates pass, the listener immediately posts a progress message ("Morty is thinking…") and starts a ticker that rewrites it every 2 seconds — first with the current activity ("looking at the media", a tool name), then with the answer itself as it streams in, previewed as plain text (half-written Markdown isn't valid HTML).

The model never sees an image. A vision pass turns every photo, video, GIF or sticker into a bracketed text note before the request is built; those notes are the model's only account of what the chat is looking at. The same machinery later describes media that the assistant's own tool calls post (diagram 5).

3Prompt assembly — static first, volatile last

The inference server caches on an exact token prefix, so the prompt is ordered to keep everything shared in front and everything per-chat at the back. The tools array is rendered into the head of the prompt by the chat template, which is why it rides every request byte-identical (memoized per chat type) and why running out of tool budget uses tool_choice: "none" instead of dropping the schemas.

4The agent loop — ask, call tools, ask again

askAssistant is a plain while (true): stream a completion, execute any tool calls, append their results to the conversation, and repeat until the model answers in plain text. Everything observable by the user (activity label, streaming preview) is fed back through callbacks; everything debuggable is emitted as trajectory events to data/trajectories/. 

flowchart TD
    START(["ctx.assistantApi.ask(messages)"]) --> DUR{"turn still under the
15 min hard cap?"}
    DUR -- "no" --> ERR(["throw — turn fails,
progress message becomes an error"])
    DUR -- "yes" --> REQ["build the request:
· conversation + tools (always)
· tool_choice = none once budget is spent
· enable_thinking = false on plain follow-ups
· remaining time as request timeout"]

    REQ --> STREAM["streaming completion
(120 s idle watchdog)"]
    STREAM -. "while text streams" .-> PART["cumulative partial →
progress message preview
(plain text, ≤ 3 900 chars)"]
    STREAM --> HAS{"response contains
tool_calls?"}

    HAS -- "yes" --> DISCARD["onPartialDiscarded —
the preview is dropped,
the user never sees it"]
    DISCARD --> EXEC
    HAS -- "no" --> EMPTY{"answer non-empty?"}
    EMPTY -- "no" --> ERR
    EMPTY -- "yes" --> RET(["return turn result:
content · sources · tool invocations
usage · media notes · confirmation id"])

    EXEC["execute the calls in order:

    BUD -- "no" --> LOOP["next iteration"]
    NUDGE --> LOOP
    LOOP --> DUR

5Tool resolution — three families behind one callTool

The merged tool list the model sees is: every skill command as a bot_* tool, then MCP tools (name collisions resolved in favor of bot tools), then built-ins. When the model calls one, resolution happens in that order. Only MCP and built-in tools may run concurrently; anything that posts into the chat keeps its place in the queue so visible order matches the order the model asked for.

Why read tools never ask permission: the tool-usage instructions in the system prompt push the model to fire read-only fetches immediately and to re-fire "live snapshot" tools (road cameras…) on every request about present conditions — history notes are stale records, not data. Volatile commands carry that directive inside their own tool description, the most local place the model will meet it.

6Write-tool confirmation — human in the loop

State-changing bot tools never run inside the loop. The call is parked as a PendingToolConfirmation bound to the requester, the reply ships with a Confirm / Cancel inline keyboard, and a separate callback_query listener settles it — 5 minutes later at most.

7Fabrication guard — delivery evidence is machine-written

Two things must never appear in a model reply: bracketed media notes and the [tools called this turn: …] marker — both are written only by the bot, after real delivery. A reply carrying either without the backing same-turn tool call is forging evidence (typically to skip re-fetching a camera), and is never delivered as-is. 

flowchart TD
    TURN(["turn result from the loop"]) --> SCAN{"unbacked media notes
or a forged tool-trace
marker in the reply?"}
    SCAN -- "no" --> OK(["deliver as-is"])
    SCAN -- "yes" --> RETRY["one corrective retry — deliberately
context-free: system + user + the forged
reply + an explicit correction
(re-reading the poison precedent
just forges again)"]
    RETRY --> SCAN2{"retry still
forges?"}
    SCAN2 -- "no" --> OK2(["deliver the honest retry"])
    SCAN2 -- "yes" --> STRIP["strip the fabrications from the text
and append the honest notice:
'the media was not delivered'"]
    STRIP --> OK3(["deliver the stripped reply"])
    RETRY -- "retry itself fails" --> STRIP

8Delivery & memory — how a turn ends and is remembered

The finished answer replaces the progress message (never a duplicate bubble), falls back to plain text when Telegram rejects the HTML, and is then written back into the session in a shape the next turn can safely learn from: the cause of side effects (the tool trace) is remembered, not the delivery claims.

Why tool traces live on the assistant's own turn: history keeps alternating user ⇄ assistant (so eviction cuts on whole exchanges), and the trace keeps the cause of a delivery visible — a later turn imitates the tool call instead of imitating the claim that media was posted. Stale delivered-media notes are scrubbed again before every request (diagram 2), so old camera fetches can never serve as precedent.
